# Cypress Test Review — `emoji-mart/cypress/e2e/emojiMart.cy.ts`

---

## Suite Overview

The `describe('Emoji Mart App')` block covers five end-to-end scenarios across the store's two main flows: the emoji listing/search page and the shopping cart. Every test starts from the root URL via a shared `beforeEach`, and each scenario is self-contained.

---

## Test-by-Test Breakdown

### 1. `displays the homepage with a list of emojis`

**What it verifies:** The page renders its title, search input, and exactly 6 emoji cards when no filter is active.

**Structure:** Assert-only — no action needed because `beforeEach` already visits `/`.

**Notable mechanics:** `cy.get('[data-testid="emoji-card"]').should('have.length', 6).and('be.visible')` runs a single DOM query and chains two assertions on the same subject. Cypress retries the entire chain until both pass — efficient and resilient.

---

### 2. `filters emojis based on search input`

**What it verifies:** Typing "Rocket" into the search bar reduces the visible emoji cards to 1, and that card shows the 🚀 emoji.

**Structure:** Act → Assert. Clean and minimal.

---

### 3. `adds an emoji to the cart`

**What it verifies:** Clicking an emoji card, clicking "Add to Cart", opening the cart via the icon, and confirming the emoji appears as a cart item.

---

### 4. `removes an emoji from the cart`

**What it verifies:** After adding an emoji, clicking the trash icon removes it and the cart shows an empty-state message.

**Structure:** The test has an intermediate assertion (`cart-item` is visible) before the "Act" step. This is a legitimate guard — it confirms the Arrange phase actually worked before executing the key action. The pattern is intentional and valid.

---

### 5. `updates the quantity of an emoji in the cart`

**What it verifies:** After adding an emoji, clicking the `+` quantity button increments the cart counter to 2.

---

## What to Celebrate

### `data-testid` selectors are used consistently for domain elements

`[data-testid="emoji-card"]`, `[data-testid="cart-item"]`, `[data-testid="cart-item-counter"]`, and `[data-testid="empty-cart"]` all follow the exact pattern Cypress officially recommends:

> *"The best selector is `data-cy`, `data-test`, `data-testid` — isolated from all changes."*
> — [Cypress Best Practices: Selecting Elements](https://docs.cypress.io/app/core-concepts/best-practices#Selecting-Elements)

These selectors survive CSS refactors, icon library upgrades, and copy changes.

---

### `beforeEach` is used correctly for test isolation

Each test visits `/` in `beforeEach`, not `before`. This guarantees the state is reset before every test, even if a previous test crashes mid-run. Cypress docs are explicit:

> *"Code put in a `beforeEach` hook will always run prior to the test — even if you refreshed Cypress in the middle of running tests."*
> — [Cypress Best Practices: Having Tests Rely on the State of Previous Tests](https://docs.cypress.io/app/core-concepts/best-practices#Having-Tests-Rely-on-the-State-of-Previous-Tests)

---

### Every test is independently runnable

No test depends on state left by a previous one. Renaming any single `it` to `it.only` and running in isolation will still pass — the gold standard of test isolation per Cypress docs.

---

### `cy.contains('h1', 'EmojiMart')` uses scoped matching

Passing an element type as the first argument to `cy.contains` prevents false matches from partial text elsewhere on the page.

---

### The AAA (Arrange–Act–Assert) comment pattern

Labeling each phase with `// Arrange`, `// Act`, `// Assert` makes the intent readable at a glance and is a strong educational practice, especially in a course context.

## Issues to Address

### Brittle: three selectors rely on Lucide CSS class names

| Location | Selector | Risk |
|---|---|---|
| Tests 3, 4, 5 | `cy.get('.lucide-shopping-cart')` | Breaks if icon library or component changes |
| Test 4 | `cy.get('button svg.lucide-trash2')` | Same |
| Test 5 | `cy.get('button svg.lucide-circle-plus')` | Same |

Lucide icon classes are generated by the library — they are presentation details, not test contracts. Cypress docs explicitly warn against selectors tied to "CSS attributes such as class":

> *"Don't target elements based on CSS attributes such as: `id`, `class`, `tag`."*
> — [Cypress Best Practices: Selecting Elements](https://docs.cypress.io/app/core-concepts/best-practices#Selecting-Elements)

**Fix:** Add `data-testid` attributes to the three buttons in the app source:

```tsx
// App.tsx — shopping cart button
<button data-testid="open-cart-button" onClick={() => setIsCartOpen(true)} ...>

// Cart.tsx — remove and quantity buttons
<button data-testid="remove-from-cart-button" ...>
<button data-testid="increase-quantity-button" ...>
```

Then the tests become:

```ts
cy.get('[data-testid="open-cart-button"]').click();
cy.get('[data-testid="remove-from-cart-button"]').click();
cy.get('[data-testid="increase-quantity-button"]').click();
```

---

### Brittle: `input[placeholder="Search emojis..."]` couples tests to UI copy

Used in tests 1 and 2. If a designer updates the placeholder text, both tests break for a reason unrelated to the feature under test.

**Fix:** Add `data-testid="search-input"` to the `<input>` in `src/components/SearchBar.tsx` and replace both occurrences:

```ts
cy.get('[data-testid="search-input"]')
```

---

### Stale / misleading comment in test 1

```ts
.should('have.length', 6) // Assuming there are 6 emojis
```

This is not an assumption — `src/data/emojis.ts` defines exactly 6 items. The word "assuming" misleads future readers into thinking the number could vary.

**Fix:** Remove the inline comment entirely, or replace it with:

```ts
.should('have.length', 6) // matches the 6 items defined in src/data/emojis.ts
```

---

### AAA label is missing for the cart-open step in tests 3, 4, and 5

All three tests click `.lucide-shopping-cart` between the `// Act` and `// Assert` sections without a comment label. It reads as part of Act, but visually it looks like floating code.

**Fix:** Either label it `// Act (continued)` or, since the cart must be open before any assertion is meaningful, include the cart open step as part of `// Arrange`:

```ts
// Arrange
cy.get('[data-testid="emoji-card"]').contains('😊').click();
cy.contains('button', 'Add to Cart').click();
cy.get('[data-testid="open-cart-button"]').click();
```

---

### Repeated setup across tests 3, 4, and 5

The same three-step sequence appears verbatim in all three cart tests. This is a maintainability risk: if the cart UX changes, three places must be updated.

**Recommended fix:** Enable the support file (set `supportFile` back to its default in `cypress.config.ts`) and add a custom command:

```ts
// cypress/support/commands.ts
Cypress.Commands.add('addEmojiToCart', (emoji: string) => {
  cy.get('[data-testid="emoji-card"]').contains(emoji).click();
  cy.contains('button', 'Add to Cart').click();
  cy.get('[data-testid="open-cart-button"]').click();
});
```

Then each test reduces to one readable line:

```ts
cy.addEmojiToCart('😊');
```

Cypress custom commands are officially documented at [Custom Commands](https://docs.cypress.io/api/cypress-api/custom-commands).
